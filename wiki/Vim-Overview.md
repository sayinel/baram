# Vim Overview

baram 의 vim 모달 편집이 **왜 지금의 모양인지를** 설명하는 페이지입니다. 무엇을 누르면 무엇이
되는지는 [사용자 문서](https://baram.ing/ko/docs/customization/palette-language-and-vim/) 가
답하고, 이 페이지는 그 아래에서 어떤 판단이 있었는지를 다룹니다.

vim 을 처음 보시는 분을 위해 배경부터 짧게 적었습니다. 익숙하시면 "세 표면, 엔진 둘" 부터
읽으셔도 됩니다.

## 배경: 모달 편집과 세 편집 표면

**모달 편집은** 같은 키가 모드에 따라 다르게 동작하는 방식입니다. normal 모드에서 `j` 는 커서를
아래로 옮기고, insert 모드에서 `j` 는 글자 `j` 를 넣습니다. 편집 명령에 수식어 키를 붙이지 않아도
되는 대신, 지금 어느 모드인지를 에디터와 사용자가 **같이 알고 있어야** 합니다. 그 합의가
깨지는 자리가 이 문서 모음의 주된 소재입니다.

baram 에는 텍스트를 편집할 수 있는 표면이 셋 있고, 셋 다 성격이 다릅니다.

```
┌─ 문서 탭 ──────────────────────────────────┐
│                                            │
│   WYSIWYG 본문                             │
│   (ProseMirror — 구문이 사라진 리치 텍스트)  │
│                                            │
│   ┌─ 코드블록 ──────────────────┐           │
│   │ CodeMirror 인스턴스          │           │
│   │ (블록 하나마다 하나씩)        │           │
│   └────────────────────────────┘           │
│                                            │
└────────────────────────────────────────────┘
              ↕  같은 문서를 다른 방식으로 본다
┌─ 소스 모드 ────────────────────────────────┐
│   CodeMirror — 마크다운 원문 그대로         │
└────────────────────────────────────────────┘
```

설정에서 **Editor → Vim 키바인딩** 을 켜면 셋이 **동시에** 켜집니다. 설정 값은 하나이고 세
표면이 그 하나를 함께 읽습니다. 사용자에게는 기능 하나입니다.

## 세 표면, 엔진 둘

구현은 기능 하나가 아닙니다. 표면마다 바탕이 다르기 때문입니다.

| 표면      | 바탕        | vim 엔진                        | 왜 그렇게 골랐나                      |
| --------- | ----------- | ------------------------------- | ------------------------------------- |
| 소스 모드 | CodeMirror  | `@replit/codemirror-vim` 어댑터 | 검증된 전체 기능을 그대로 쓸 수 있다  |
| 코드블록  | CodeMirror  | 같은 어댑터                     | 소스 모드와 바탕이 같다               |
| WYSIWYG   | ProseMirror | **자체 엔진**                   | 리치 텍스트 위의 vim 은 기성품이 없다 |

코드블록과 소스 모드는 **같은 어댑터 모듈을 공유합니다.** 모듈을 동적으로 불러오고 그 약속을
캐시해 두므로, 소스 모드를 드나들 때도 코드블록이 여럿 열려도 모듈은 한 번만 내려받습니다.

엔진이 둘이라는 사실은 사용자에게 드러나지 않아야 하지만, 완전히 감춰지지도 않습니다. 예를 들어
**모드 집합이 다릅니다** — 자체 엔진은 normal · insert · visual 셋을 갖고, 어댑터를 쓰는 두
표면은 거기에 replace(`R`)를 더해 넷을 갖습니다. 어댑터가 이미 갖고 있는 것을 자체 엔진에서
일부러 다시 만들지 않은 결과입니다.

## 왜 WYSIWYG 만 자체 엔진인가

vim 의 모델은 **줄과 칼럼으로 된 평문 버퍼를** 전제합니다. 소스 모드와 코드블록은 실제로 그것이라
검증된 어댑터를 쓰지 않을 이유가 없습니다. 직접 만들면 기능의 긴 꼬리를 처음부터 다시 만드는
일이고, 그렇게 얻는 것이 없습니다.

ProseMirror 문서는 사정이 다릅니다. 트리이고, 원자 노드(수식 · mermaid · 이미지 · hr 처럼 안으로
커서가 들어가지 않는 것들)가 있고, 테이블이 있습니다. 그리고 결정적으로 **"한 줄" 이라는 것이
문서에 존재하지 않습니다.**

그래서 `dd` 가 무엇을 지우는지 답하려면 줄을 **먼저 정의해야** 합니다.

- 수식 블록 하나는 한 줄인가요?
- hardBreak 로 나뉜 문단은 몇 줄인가요?
- 테이블 행 하나는 어떻게 세나요?

이 질문들의 답이 [Architecture](Vim-Architecture) 의 행 모델이고, 기성품 어댑터가 대신 내려 줄
수 있는 결정이 아닙니다.

그 위에 브라우저 층의 문제가 얹힙니다. 모달 상태의 뷰는 non-editable 이어야 하는데(아래
"한국어는 1급 시민이다" 에서 이유를 설명합니다), 그러면 ProseMirror 의 selection 동기화가
멈춥니다. [WebKit selection churn](Vim-WebKit-selection-churn) 이 그 수사 기록입니다.

**리치 텍스트 위의 vim 이 기성품으로 없는 이유는 키 바인딩이 아니라 이런 층에 있습니다.**

블록별로 더해지는 것은 경계 UX(블록 안으로 들어가고 나오는 규칙)와 그 경계를 성립시키는
배선입니다. 모듈이 로드되기 전에 세우는 동기 editing-host 장벽, PM 과 CM 사이의 핸드오프, 섬
상태 피드가 거기 들어갑니다. 자세한 것은
[Input islands and block entry](Vim-Input-islands-and-block-entry) 에 있습니다.

## 한국어는 1급 시민이다

한국어 입력은 나중에 덧붙인 대응이 아니라, **각각 다른 층에 박혀 있는 세 가지 처치입니다.**
사후에 끼우면 경로마다 동작이 갈리기 때문입니다.

**1. IME 차단은 선언적입니다.** normal 과 visual 에서는 **editing host 자체를 제거합니다.**
WebKit 이 조합할 곳이 없으니 자모가 문서에 새지 않습니다. 그 아래에 입력 취소 가드가 한 겹 더
깔립니다 — 실기기에서 잰 결과가 정한 순서입니다. 대신 뷰가 non-editable 이 되는 대가를
치르고, 그 대가가 위에서 말한 selection 문제를 부릅니다. 사는 곳은 뷰의 editable 판정과 별도의
입력 가드 둘입니다.

**2. 명령 키가 한글 레이아웃에서 그대로 동작합니다.** 한글이 켜진 채 `j` 를 누르면 `event.key`
는 `ㅓ` 입니다. 키 정규화 층이 **자모가 글자키에서 나왔을 때 그 물리 글자를 명령으로 읽고**,
원래 문자는 따로 실어 보냅니다. 두벌식이 이 조건을 만족합니다. 좁힘이 이렇게 빡빡한 것은
의도된 것으로, dvorak 같은 라틴 리매핑과 기호 키가 다치지 않게 하기 위해서입니다. 사는 곳은
core 의 키 어휘입니다.

**3. `f` 뒤의 `ㄱ` 은 초성 검색입니다.** `f`·`t` 의 타겟은 리터럴 문자로 받아야 하므로, 물리키가
아니라 함께 실어 보낸 원래 문자를 씁니다. 한글 타겟은 한글을 찾습니다. 사는 곳은 core 의 문자
매칭입니다.

세 처치가 서로 다른 층에 있다는 것이 요점입니다. 한 층에서만 처리하려 했다면 나머지 두 경로가
조용히 어긋났을 것입니다.

## 읽는 순서

1. **[Architecture](Vim-Architecture)** — 여기서 시작하시면 좋습니다. 층과 경계, 그리고 경계가
   왜 거기 그어졌는지를 다룹니다. 나머지 페이지는 이 그림 위의 이야기입니다.
2. 그 다음은 관심 영역으로 가시면 됩니다. selection 이 되돌려지는 증상을 만나셨다면
   **[WebKit selection churn](Vim-WebKit-selection-churn)** 으로 바로 가시는 편이 낫습니다 —
   증상이 엉뚱한 곳을 가리키는 버그라, 모르고 파면 이미 반증된 길을 다시 밟게 됩니다.
3. **[Code map](Vim-Code-map)** — 파일 위치를 찾으실 때. 경로는 그 페이지에만 삽니다.
4. **[Decisions and history](Vim-Decisions-and-history)** — "왜 이건 안 만들었나" 가 궁금하실 때.

## 어디까지 와 있나

**척추는 세 표면 모두 구현돼 있습니다** — 모드(normal · insert · visual) · 모션 · 오퍼레이터
(`d`/`c`/`y`) · find(`f`/`t`) · register · `/` 검색.

남은 것은 [#372](https://github.com/sayinel/baram/issues/372) 에 티어 1~4 로 삽니다. 티어 1 이
`.` 반복 · 텍스트 오브젝트 · `r` · curswant 이고, 티어 4 가 매크로 · 마크 · named register 입니다.

**이 골격은 변하지 않습니다.** 어느 티어의 무엇이 착지했는지만 이슈에서 움직이므로, 정확한
현황은 여기가 아니라 그 이슈를 보셔야 합니다.
