# 플러그인 회수(revocation) — 설계

§69 플러그인 마켓플레이스 / §260 실행 모델의 후속. 2026-08-01.

## 왜 필요한가

Baram은 플러그인 번들을 직접 호스팅한다 (`sayinel.github.io/baram-plugins/plugins/…`). 이 선택에는 비용이 따른다 — **제3자 코드가 우리 도메인에서 배포된다.** 그런데 지금 그 비용에 대응하는 능력이 없다. 악성 커뮤니티 플러그인이 발견되면 할 수 있는 일은 인덱스에서 항목을 빼는 것뿐이고, 그건 **신규 설치만 막는다.** 이미 설치한 사용자에게는 아무 일도 일어나지 않는다.

비교 대상 두 곳이 정반대를 택했고, 그 차이는 정확히 이 지점이다.

| | Obsidian | VS Code | Baram (현재) |
|---|---|---|---|
| 바이트 보관 | 저자 GitHub 릴리스 | Microsoft | **우리** |
| 버전 고정 | ✗ (저자 릴리스 자동 추적) | 서명 | ✓ 인덱스의 SHA-256 |
| 신규 설치 차단 | ✓ 목록에서 제거 | ✓ | ✓ |
| **설치된 것 회수** | ✗ | ✓ 강제 언인스톨 | **✗ ← 이 문서** |

Obsidian은 포인터만 갖고 있어서 구조적으로 회수할 수 없다. Microsoft는 호스팅하므로 사용자 기기에서까지 지운다. **호스팅은 안전을 만들지 않고 대응 능력을 만든다** — Microsoft는 호스팅+서명을 하고도 인포스틸러·랜섬웨어를 반복해서 배포했다(`C++ Playground`는 제거 전 17,000회 설치). 우리는 호스팅의 비용을 이미 지불하고 있으므로, 대응 능력을 갖추지 않으면 **downside만 지고 upside는 안 가져가는 상태**다.

## 등급이 필요하다 — 데이터가 그렇게 말한다

Obsidian의 `community-plugins-removed.json`은 현재 **369개** 항목이고, 사유를 보면 대부분 보안 문제가 아니다:

- `"Features merged into Commander plugin"`
- `"ID changed, no response from developer after 30 days"`
- `"Developer banned from GitHub"`

이런 항목까지 로드 거부하면 **사용자가 잘 쓰고 있던 기능을 위생상의 이유로 빼앗는 것**이 된다. 반대로 인포스틸러를 목록에서 빼는 것으로 끝내면 아무도 보호받지 못한다. 하나의 "제거" 개념으로는 둘 다 틀린다.

따라서 회수는 **세 등급**으로 나눈다.

| 등급 | 뜻 | 앱 동작 | 예 |
|---|---|---|---|
| `malicious` | 사용자에게 해를 끼침 | **로드 거부** + 이유 표시 + 제거 버튼 | 데이터 탈취, 랜섬웨어, 권한 우회 |
| `vulnerable` | 취약하지만 악의는 없음 | **로드하되 경고 배너** + 업데이트 유도 | 취약한 의존성, 안전하지 않은 요청 |
| `unlisted` | 위생 — 사용자에게 위험 없음 | **아무 일도 안 함**. 신규 설치만 차단 | 저자 응답 없음, 다른 플러그인에 병합, 중복 id |

`unlisted`가 기본값이어야 한다. 대부분의 제거가 여기 해당하고, 이 등급은 이미 설치한 사용자를 건드리지 않는다.

## 삭제하지 않는다

`malicious`여도 **파일을 말없이 지우지 않는다.** 로드를 거부하고 이유를 보여주고 제거 버튼을 준다.

근거는 Microsoft다 — 수백만 명이 쓰던 확장을 잘못 제거하고 공개 사과했다. 회수는 **오발할 수 있는 권한**이고, 오발했을 때 사용자가 되돌릴 수 있어야 한다. 로드 거부는 되돌릴 수 있고(회수 철회 시 다음 실행에 복구), 파일 삭제는 되돌릴 수 없다.

같은 이유로 회수는 **사용자에게 보이는 사건**이어야 한다. 조용히 동작이 바뀌면 사용자는 앱이 고장난 줄 안다.

## 목록은 어디에 사는가

**인덱스와 별도 파일**: `sayinel.github.io/baram-plugins/revoked.json`

인덱스 안에 넣지 않는 이유 세 가지:

1. **캐시 수명이 달라야 한다** (아래)
2. **공식·커뮤니티 양쪽에 공통 적용된다** — 우리가 만든 것도 회수해야 할 수 있다. 인덱스가 둘로 갈리면(공식/커뮤니티 분리) 회수 목록이 어느 쪽에 속하는지 애매해진다
3. **작다.** 자주 받아도 부담이 없고, 그래야 자주 받을 수 있다

### 형식

```json
{
  "version": 1,
  "revoked": [
    {
      "id": "some-plugin",
      "versions": { "gte": "2.0.0", "lt": "2.0.4" },
      "severity": "malicious",
      "reason": "Exfiltrates vault contents to a third-party server",
      "reasonKey": "plugin.revoked.exfiltration",
      "since": "2026-08-01"
    }
  ]
}
```

- `versions`는 **구조체**이지 semver 범위 문자열이 아니다. `"*"`(전 버전) 또는 `eq`/`gt`/`gte`/`lt`/`lte` 중 하나 이상을 담은 객체이며, 있는 경계를 모두 AND로 묶는다. ‼️문자열 범위(`">=2.0.0 <2.0.4"`)는 **항목이 조용히 버려진다** — 이 문서가 한때 그렇게 예시를 적어놨고, 보안 리뷰가 "새벽 2시에 문서대로 쓰고 배포하면 문서는 200으로 받아들여지는데 항목만 사라진다"고 지적했다. **버전 단위로 회수한다** — "2.0.0~2.0.3이 악성이고 2.0.4에서 고쳐졌다"가 실제로 흔한 형태다. 플러그인 전체 회수는 범위를 `*`로 주면 표현된다
- `reason`은 영어 원문, `reasonKey`는 i18n 키(선택). 키가 있으면 그것을 쓰고 없으면 원문을 쓴다 — 사유는 사람이 쓰는 자유 문장이라 전부 번역할 수 없다
- `since`는 표시용

## 캐시 수명 — 여기가 보안상 중요한 지점

현재 `registry-client.ts`는 페치 실패 시 **무기한 stale 캐시를 반환**한다:

```ts
} catch (err) {
  if (store.registryCache) {
    logger.warn("[Registry] Fetch failed, using stale cache:", err);
    return store.registryCache;
  }
```

브라우즈 인덱스에는 맞는 동작이다(목록이 낡아도 해가 없다). **회수 목록에는 맞지 않는다** — 이 규칙을 그대로 쓰면 네트워크를 막는 것만으로 회수가 무력화된다.

그렇다고 fail-closed(목록을 못 받으면 플러그인 로드 안 함)로 갈 수도 없다. Baram은 로컬 우선 앱이고, 비행기에서 노트를 쓰는 사용자가 플러그인을 잃으면 안 된다.

**채택하는 규칙:**

1. 회수 목록을 **디스크에 영속 저장**한다 (메모리 캐시가 아니라). 앱을 껐다 켜도 남는다
2. 로드 시점에는 **항상 저장된 목록을 적용한다.** 네트워크 상태와 무관하다
3. 목록 갱신은 **백그라운드로 자주** 시도한다 (앱 시작 시 + 마켓플레이스를 열 때). 실패해도 조용히 넘어간다
4. 목록이 **N일 이상 낡으면** 플러그인 설정 화면에 표시한다 — 차단하지 않고 알리기만 한다

이 규칙에서 공격자는 "회수 이후 사용자가 **한 번도** 목록을 받지 못하게" 막아야 한다. 한 번이라도 받으면 오프라인에서도 계속 적용된다. 이게 로컬 우선 앱에서 낼 수 있는 최선이다.

> ‼️ 목록 자체의 무결성은 **HTTPS + Pages 호스트 신뢰**에 의존한다. 인덱스와 같은 신뢰 루트다. 서명을 붙이면 이 의존이 사라지지만, 그건 별도 단계다(아래).

## 어디에 끼우나

- 검사 지점: `plugin-loader.ts`의 `loadPlugin()` — 티어 분기(`trusted`/`sandboxed`)보다 **앞**이어야 한다. 회수된 플러그인은 어느 티어로도 실행되면 안 된다
- 설치 지점: 설치 전에도 검사한다. 회수된 버전은 애초에 설치되지 않는다
- 표시: 플러그인 목록의 해당 항목 + 상세 화면. `unlisted`는 표시하지 않는다(사용자에게 의미 없음)

## 하지 않는 것

- **원격 코드 실행이 아니다.** 목록은 데이터일 뿐이고 앱이 해석한다
- **파일 삭제가 아니다.** 위 참조
- **텔레메트리가 아니다.** 목록을 받아올 뿐 무엇이 설치돼 있는지 보내지 않는다
- **개발 중(dev) 플러그인에는 적용하지 않는다.** 로컬 경로에서 로드하는 것은 개발자 본인 코드다

## 나중 단계

**회수 목록 서명.** 지금은 Pages 호스트가 신뢰 루트다. 목록에 서명하고 앱이 공개키로 검증하면, 호스트가 침해돼도 가짜 회수(정상 플러그인 무력화)나 회수 삭제가 불가능해진다. 공식 번들 서명과 같은 작업이므로 함께 하는 것이 자연스럽다.

## 열린 질문

- `N일` 낡음 경고의 N — 30일을 제안한다. 근거는 약하며, 실사용 후 조정
- `vulnerable` 등급의 배너를 사용자가 닫을 수 있게 할지. 닫을 수 있으면 무시되고, 못 닫으면 성가시다
